## Build and test
- `sh build.sh` (or `node scripts/build.mjs`) joins `src/` in the order in `src/ORDER.txt` into `inkling.html`. All modules share one scope, and the order matters. A new module goes into `ORDER.txt`.
- **Desktop app (Tauri 2):** `npm install` once, then `npm run app` to start it (`tauri dev --no-dev-server`, so the page has the same address as the installed app), `npm run app:build` for an installer. Needs Rust. See ARCHITECTURE.md section 2b.
- **Test setup (once):** `pip install -r requirements.txt` then `python3 -m playwright install chromium`. Run `npm install` too, so test4 can use the local three.js.
- **Tests:** `sh tests/run_all.sh` runs everything, or run one with `python3 tests/test12.py`.
- **Simulated environment:** the tests run the built file in Chromium with a simulated Claude runtime (`mock3d.js`, `mock_lang.js`, `mockprod.js`), a simulated desktop app (`mock_desk.js`, test19) and a stand-in 3D engine (`fake_three.js`).
- **After every change:** build, then run the tests that touch the change, then the whole suite before finishing.

## Rules
- **Platform layer:** only `src/11_store.js`, `src/11b_platform.js` and `src/11c_ai.js` may talk to the host (`caps.*` in Claude, `Desk`/`deskCall` in the desktop app) or to AI services. Everything else uses `Store`, `AI`, `Files`, `Shared`, `Live`, `Me`, `Downloads`, `Capture`, `WordBridge` (also `findDocs` / `openDoc`), `PadLink`, `PadRelay` and `Platform`. The native side of the desktop app is `src-tauri/src/lib.rs`; a new native command goes there and into the table in ARCHITECTURE.md 2b.
- **Three hosts:** every change must keep working inside Claude, in the desktop app and in the browser version (`Platform.host`). Messages that name where a feature works use `Platform.aiWhere` / `Platform.shareWhere`; messages about the AI use `AI.name`, not “Claude”.
- **AI:** every `AI.text` / `AI.json` call passes `task: '<id>'` from `AI_TASKS` (`src/11d_ai_tasks.js`). A new AI feature gets a new task; then run `node scripts/ai-docs.mjs` (updates `docs/AI.md`). Write prompts any model can follow: what to do, the exact answer format, and validate the answer. Details in `docs/AI.md`.
- **Frozen data:** data read from the database can be frozen, so always `deep()` copy it.
- **Objects:** objects get unique numbered names through `addObj` and `uniqueName`. Pinned objects (`o.pin`) live on `view.pinSurf`.
- **Menus:** use `openMenu(anchor, items)`, where items support `sub:`, `checked:` and `header:`. Panels use `openPop`. A click inside a `.menu` or `.pop` must never close the open panel.
- **Docs:** keep ARCHITECTURE.md up to date whenever modules, data shapes or the export format change.
- **Word link:** the app, the bridge and the Word panel share `src/48_wordsync.js`; change the message format or the paragraph model in all three, and run `node tests/wordsync_unit.mjs`, test28 and test31. The panel must never write into a paragraph with a picture; in tables it only sets the values of cells that changed (tables with a picture stay locked).
- **Backups:** never break reading of backup format 1 (`inkling-backup-*.json`, now saved as `cortex-scribe-backup-*.json`). Users move their notes over with it.
- **The name:** user-visible text says Cortex Scribe. Never rename stored names: storage keys (`inkling:`), the backup marker `"app": "Inkling"`, `inkling.html`, `Documents/Inkling` and the Tauri identifier (ARCHITECTURE.md top).

## Pinned priorities (agreed November 2026, see `docs/ROADMAP.md`)
1. Reliability first: real phone and tablet tests, never losing data, sync between devices.
2. The study loop: subjects, projects, calendar and the coach (`docs/design/`).
3. Imports from OneNote, Goodnotes and Word, so others can switch.
4. Keep it simple: good defaults, advanced things hidden until needed.
5. Real users: 5–10 classmates for one semester; fix what annoys them.
